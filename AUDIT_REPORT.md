## АКТУАЛЬНЫЙ СТАТУС (обновлено: 2026-08-29 — звук + устранение RPC-таймаута `test:solver`)

Полный аудит проекта на долгосрочную стабильность: звуковые эффекты доведены до 20/20 подключённых, найден и устранён двухуровневый баг тестовой инфраструктуры тяжёлых BFS-тестов.

**Звук.** Сгенерированы и подключены 4 недостающих файла (`gate_swing.mp3`, `grandpa_mumble_1/2/3.mp3`); статус — 20/20 звуковых эффектов подключены (`AUDIO_ASSETS_REQUIRED.md`).

**Баг `test:solver` — RPC-таймаут, диагностирован и устранён на двух уровнях:**

1. **Синхронная блокировка event loop внутри `solve()`.** BFS-решатель — синхронная функция; на тяжёлых уровнях (глава 10, 7×7, до ~400 000 состояний) один вызов мог занимать 40–55с. Внутренний RPC vitest (`onTaskUpdate`) имеет захардкоженный таймаут 60000мс без публичного API для override — при долгом синхронном блоке процесс `vitest` падал целиком (`Unhandled Error: Timeout calling "onTaskUpdate"`), обрывая прогон: уже пройденные тесты отчитывались как passed, но оставшиеся файлы вообще не запускались (ложное ощущение частичного успеха). Точечные `yieldToEventLoop()` между вызовами `solve()` не спасали, если один вызов сам по себе был близок к порогу.
   **Фикс**: BFS-ядро (`src/core/solver.ts`) вынесено в generator (`solveSteps()`) с внутренними точками приостановки (между уровнями BFS-глубины и каждые 2000 узлов фронта). `solve()` — синхронная обёртка без изменения поведения. Новая `solveAsync()` отдаёт event loop по РЕАЛЬНОМУ времени (250мс) внутри самого поиска — защита не зависит от размера уровня. Аналогичная `analyzeIceImpactAsync()` добавлена в `src/core/ice-impact.ts`. Все тяжёлые тестовые файлы мигрированы на асинхронные версии.
2. **Межфайловая GC-пауза.** После фикса (1) тот же RPC-таймаут продолжал случаться, но уже на границе между файлами внутри одного `singleFork`-процесса: карты состояний BFS (до ~400 000 записей на уровень) накапливались от файла к файлу, и после 4+ тяжёлых файлов подряд stop-the-world GC-пауза превышала 60с.
   **Фикс**: новый раннер `scripts/run-solver-tests.mjs` запускает каждый тяжёлый тестовый файл в отдельном процессе `vitest run <файл>` — память гарантированно освобождается ОС между файлами. `npm run test:solver` переключён на этот раннер.

**Итог верификации**: `npm run test:solver` — 10/10 файлов passed, 0 unhandled errors (устойчиво воспроизведено). `npm run typecheck`, `npm run lint`, `npm test` (534/534) — без регрессий. Подробности и тайминги — см. `CHANGELOG.md`, запись от 2026-08-29.

## 3. ПОДТВЕРЖДЁННЫЕ ОШИБКИ

### HIGH

**[BUG-1] Реклама без защитного таймаута — риск soft-lock уровня**
- Критичность: HIGH · Уверенность: высокая (подтверждено кодом)
- Файл: `src/platform/yandex.ts:329-408` (`showInterstitial`, `showRewarded`); потребители — `src/ui/app.ts:1214-1273` (skip/hint).
- Подтверждение: `Promise` резолвится только из колбэков `onClose/onError/onOffline`. Ни таймера, ни `finally`. Если SDK не вызовет ни один колбэк (известный на практике сценарий), промис висит вечно, `adActive` остаётся `true`, а в hint/skip кнопка остаётся `disabled` и `bv.interactive = false`.
- Сценарий: игрок жмёт «Подсказка → смотреть рекламу»; SDK открывает и закрывает объявление, но `onClose` теряется. Поле навсегда неинтерактивно; выход только перезагрузкой.
- Последствие: жёсткая блокировка прохождения, потеря сессии, негативные отзывы на модерации.
- Причина: отсутствует предохранитель на «немой» SDK.
- Исправление: добавить `setTimeout` (например 20–30 с) внутри промиса, который вызывает `finish()` (для rewarded — **без** награды, `rewarded` не выставлять). Очищать таймер в `finish()`.
- Риск исправления: низкий; изменение локально в двух методах.
- Нужный тест: unit — «reward-промис резолвится по таймауту без onRewarded ⇒ false и adActive сброшен».

**[BUG-2] ~~Ранг лидерборда смещён на +1~~ — ОТОЗВАН**
- ⛔ **Неверный вывод.** Документация Яндекса: rank 0-базовый, `+1` корректен. Код и тесты правы. Оставлено для истории.
- Критичность: ~~HIGH~~ отозвано · Уверенность первоначальная: высокая (оказалась ошибочной)
- Файл: `src/platform/yandex.ts:194-198` (`getLeaderboard`), `220-226` (`getMyRank`).
- Подтверждение: код делает `rank: (entry.rank ?? index) + 1` и `rank: (mine.rank ?? 0) + 1`. Тест `tests/yandex.test.ts:193,214-219` подаёт в мок `rank: 0` и ждёт `1`, `rank: 6` → `7`, то есть кодирует нуль-базовое допущение. В реальном SDK Яндекса `entry.rank` — это фактическое место, начинающееся с **1**. `src/platform/mock.ts:77-93` формирует ранги корректно 1-базово, поэтому в dev всё выглядит правильно, а на реальной платформе первое место покажется как «2».
- Сценарий: игрок №1 в таблице видит «2», своё место — на 1 больше реального.
- Последствие: у всех игроков некорректный ранг в обеих таблицах.
- Исправление: убрать `+1` для ветки с присутствующим `rank`; оставить fallback `index + 1` только когда `rank` отсутствует: `rank: entry.rank ?? index + 1`. Синхронно поправить тесты (они закрепляют неверное поведение — «не доверять названиям тестов»). Сверить с актуальной документацией Яндекса перед правкой.
- Риск исправления: низкий, но требует пересмотра тестов.
- Нужный тест: мок с `rank: 1` ⇒ ожидание `1` (после сверки с доками).

**[BUG-3] ~~`submitScore` может не отправлять счёт~~ — ОТОЗВАН**
- ⛔ **Неверный вывод.** `setScore` — актуальный метод, `isAvailableMethod('leaderboards.setScore')` — верная строка (подтверждено доками). Код правильный. Оставлено для истории.
- Критичность: ~~HIGH~~ отозвано · Уверенность первоначальная: средняя (оказалась ошибочной)
- Файл: `src/platform/yandex.ts:174-183`.
- Подтверждение: `if (ysdk.isAvailableMethod && !(await ysdk.isAvailableMethod('leaderboards.setScore'))) return;`. - Риск исправления: низкий.
- Нужный тест: мок без `setScore`, только `setLeaderboardScore` + `isAvailableMethod`, проверка что запись состоялась.

- **[BOSS-1 HIGH] Финальный босс 100 не открывал Высшую лигу.** Последняя фаза шла через `onBossPhaseDone` → `recordResult`+`markBossDone`+`showBossVictory`, минуя кампанийную логику `finishLevel` (там жили `markCampaignDone`/финальная сцена/анлок лиги). Итог: пройдя кампанию через босса 100, игрок не получал лигу/легендарный скин. **Исправлено:** выделен общий метод `completeCampaignFinale()` (идемпотентно помечает кампанию, один раз показывает финальную сцену), вызывается и из `finishLevel`, и из `onBossPhaseDone` для слота 100. Повтор не выдаёт награды заново. Регрессия покрыта e2e (открытие лиги один раз + повтор без наград).
