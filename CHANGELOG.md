### Fixed — критический баг тестовой инфраструктуры (RPC-таймаут `test:solver`)
- **Корневая причина.** BFS-решатель (`src/core/solver.ts`) — синхронная функция; на тяжёлых уровнях (7×7, глава 10, ~400 000 состояний) один вызов `solve()` мог занимать 40–55с реального времени, полностью блокируя event loop. Внутренний RPC vitest (birpc, `onTaskUpdate`) захардкожен на таймаут 60000мс без публичного API для override — при долгом синхронном блоке репортёр не успевал получить ответ, и **весь процесс** `vitest` падал с `Unhandled Error: [vitest-worker]: Timeout calling "onTaskUpdate"`, обрывая прогон и оставляя ещё не запущенные тестовые файлы невыполненными (при этом уже пройденные тесты отчитывались как «passed» — ложная видимость благополучия).
- **Первая (недостаточная) попытка** — точечные `await yieldToEventLoop()` между вызовами `solve()` — не защищает, если ОДИН вызов сам по себе близок к порогу таймаута: yield между вызовами не спасает от долгого блока внутри одного вызова.
- **Архитектурное решение — `solveAsync()`.** BFS-ядро вынесено в generator (`function* solveSteps()`) с внутренними точками приостановки (между уровнями глубины BFS и каждые 2000 обработанных узлов фронта). `solve()` остаётся синхронной обёрткой без изменения поведения (прод-код не затронут). Новая `solveAsync()` — асинхронная обёртка, отдающая event loop по РЕАЛЬНОМУ времени (`yieldEveryMs`, по умолчанию 250мс) — защита не зависит от размера уровня или нагрузки CPU. Аналогично добавлена `analyzeIceImpactAsync()` (`src/core/ice-impact.ts`) для тестов, использующих постфактум-абляцию льда.
- Все тяжёлые тестовые файлы (`levels-solver-1..6.test.ts`, `boss.test.ts`, `elite.test.ts`, `endless.test.ts`, `ice.test.ts`) мигрированы с `solve()`/`analyzeIceImpact()` на `solveAsync()`/`analyzeIceImpactAsync()`.
- **Вторая находка — межфайловая GC-пауза.** Даже после устранения блокировок внутри отдельных вызовов, `vitest run` с `pool: 'forks', singleFork: true` продолжал падать по тому же RPC-таймауту, но уже на границе между файлами: BFS хранит карты состояний до ~400 000 записей на уровень, и внутри одного процесса эти карты накапливаются от файла к файлу — после 4+ тяжёлых файлов подряд стоп-the-world GC-пауза на границе следующего файла превышала 60с.
- **Решение — изоляция процессов.** Новый раннер `scripts/run-solver-tests.mjs` запускает каждый тяжёлый тестовый файл в СОБСТВЕННОМ дочернем процессе `vitest run <файл>` — память полностью освобождается ОС между файлами. `npm run test:solver` теперь вызывает этот раннер вместо одного `vitest run --config vitest.solver.config.ts` со всеми файлами сразу.
- **Итог**: полный прогон `npm run test:solver` — 10/10 файлов passed, 0 unhandled errors (было: падение после 4–5 из 10 файлов на протяжении нескольких прогонов).

## 2026-08-27 — Боссы-ремиксы, par-perfect и воронка освоения

### Added
- **Фазы боссов — ремиксы уровней, а не копии.** Каждая фаза пяти боссов строится через `buildRemix` (`bossPhaseLevel` в `boss.ts`): отражение поля + сдвиг одной фигуры ломают заученный маршрут, двор остаётся узнаваемым. `par`/`par2` всех 11 ремиксов объявлены в данных и сверяются решателем (`tests/boss.test.ts`); проходимость и звезда требуемых фаз доказаны solver'ом.
- **par-perfect («уровень освоен»):** победа 3★ в пределах оптимума — разово +1 подсказка (сейв-поле `masteredLevels`, sanitize/merge без version bump), note `win-par-perfect` и аналитика `level_mastered`.
- **Реплей идеального решения:** в окне победы при par-прохождении кнопка «идеальное решение» — solver строит путь, BoardView проигрывает его ход за ходом (HUD заблокирован на время показа).
- **Живой счётчик ходов в HUD:** цель подкрашивается — зелёный в пределах `par`, красный за `par2` (`hud-par-ok`/`hud-par-warn`).
- **Аналитика воронки:** `level_exit` (уход с уровня до победы).

### Tests
