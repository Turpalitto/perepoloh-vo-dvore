# Переполох во дворе — правила проекта

Парковочная головоломка (HTML5, Яндекс Игры). TypeScript strict + Vite, без игрового движка: поле — SVG, UI — DOM.

## Команды
- `npm run dev` — дев-сервер
- `npm run typecheck` — tsc --noEmit
- `npm run lint` — eslint (floating promises и т.п., что tsc не ловит)
- `npm run check` — typecheck + lint + unit + solver + verify:ice/planks/chickens/held + verify:docs одной командой; гонять перед коммитом
- `npm test` — unit-тесты (vitest)
- `npm run solve` — решатель по всем уровням (печатает оптимум)
- `npm run analyze` — сложность и дубликаты всей кампании (`-- --json out.json`; ~2.5 мин, exit 1 только при дефектах)
- `npm run build` — production-сборка в `dist/`
- `npm run verify:dist` — проверка production-архива (запрещённые маркеры, домены, промо-PNG)
- `npm run verify:ice` — доказательство, что каждая ледяная клетка кампании значима (входит в `check`)
- `npm run verify:planks` / `verify:chickens` / `verify:held` — то же для досок, кур и held-кнопки (входят в `check`)
- `npm run verify:docs` — сверка чисел в документах с данными (входит в `check`); `-- --write` перегенерирует `GENERATED_PROJECT_STATS.md`
- `npm run check:release` — всё перед публикацией: `check` + solve + build + verify:dist + e2e
- `npm run e2e` — браузерные тесты (playwright, требует `npm run build`)

## Жёсткие правила
- Игровая логика (`src/core/`) — чистые функции без DOM; всё состояние сериализуемо.
- Уровни только в `src/levels/levels.json`; новый уровень не требует правок кода.
- Каждый уровень обязан проходить валидатор и решатель; `par` в JSON должен совпадать с оптимумом решателя (проверяется тестом `levels.test.ts`).
- Лёд (`ice`) ставится только там, где он несёт вес: без любой отдельной клетки оптимум обязан падать, и у клетки должна быть роль «проезд» либо «запрет стоянки» (`npm run verify:ice`). Декоративный лёд запрещён — механика уже один раз оказалась пустой.
- **Механику сравнивают не с пустотой, а с самым дешёвым способом изобразить то же самое.** «Без неё оптимум падает» — недостаточное доказательство: так проходит любая преграда. Доска обязана отличаться ото льда И от стены, курица — от стены в каждой из своих клеток, held-кнопка — от режима `once`. Правило выведено дорого: хрупкие доски прожили в лиге целый цикл, давая ровно тот же оптимум, что обычная стена (17/17/17 и 18/18/18), и `verify:planks` их пропускал, потому что унаследовал правило значимости ото льда. Новая механика без такой проверки в `check` не заводится.
- Доски (`planks`) контентом не наполнять, пока не изменено правило: перебор 1228 постановок не нашёл ни одной клетки, где разрушение поднимает оптимум (`scripts/plank-scan.ts` воспроизводит). Доска играет, только если решение пересекает клетку дважды, а в кратчайших решениях на 6×6 этого не бывает.
- Никакого прямого обращения к `YaGames` вне `src/platform/yandex.ts`; игра использует только интерфейс `Platform`.
- Не ослаблять типизацию и не отключать тесты ради сборки.
- Тексты интерфейса — русские.
- Перед правкой `src/platform/yandex.ts` сверять точное имя метода/формат по актуальной документации Яндекс Игр (yandex.com/dev/games/doc), не по памяти и не по комментариям в коде — SDK менялся (например `setScore` вместо устаревшего `setLeaderboardScore`, rank у Яндекса 0-базовый).

## `src/ui/app.ts` (god object, ~1700 строк)
Известный риск, оставлен осознанно — не рефакторить заранее «про запас».
- **Не разбивать целиком одним PR.** Выносить контроллер (`AdController`, `TVNavigationController`, `ScreenRouter`, ...) только тогда, когда добавляешь/меняешь фичу в этой конкретной области — рефактор обосновывается задачей, а не архитектурой самой по себе.
- Первый кандидат при следующей причине тронуть рекламу — `AdController` (уже частично изолирован: `adHandlers`, `showInterstitial`/`showRewarded` вызовы). Второй — `TVNavigationController` (`moveTVFocus`/`focusTVDefault`/`onTVKeyDown` почти не трогают остальное состояние).
- После любого выноса — обязательно `npm run check` и `npm run e2e` (49 тестов покрывают lifecycle экранов, paus/реклама, TV-навигацию — это единственная страховка от регрессий при разборке).

## Правила работы с SVG
- использовать SVG преимущественно для иконок, UI и простой игровой графики;
- не вставлять один и тот же большой inline-SVG многократно;
- повторяемые изображения оформлять как переиспользуемые компоненты или SVG-спрайт;
- не использовать SVG с тысячами точек без оптимизации;
- удалять metadata, скрытые слои и лишние группы из экспортов Figma;
- задавать корректный viewBox;
- не фиксировать одновременно width и height, если элемент должен быть адаптивным;
- не масштабировать SVG через transform без необходимости;
- избегать тяжёлых filter, blur и drop-shadow внутри массово повторяемых объектов;
- учитывать prefers-reduced-motion для SVG-анимаций;
- не помещать игровую логику внутрь SVG;
- проверять производительность на мобильном устройстве;
- прогонять SVG через оптимизатор, например SVGO;
- декоративным SVG задавать aria-hidden="true";
- интерактивным элементам обеспечивать доступное название и достаточную область нажатия.

## Модель для анализа
Использовать Fable 5 для центрального анализа, архитектурных решений, реализации и финального ревью. Вспомогательные агенты могут исследовать отдельные области, но их выводы обязательно перепроверять самостоятельно.

## Структура
- `src/core/` — типы, правила движения, решатель, валидатор (покрыто unit-тестами)
- `src/levels/` — данные уровней
- `src/platform/` — интерфейс платформы, mock и Яндекс SDK
- `src/ui/` — экраны, SVG-рендер поля, ввод
- `src/game/` — звук, сохранения, конфиг прогрессии
- `scripts/solve.ts` — отчёт решателя по уровням
- `tests/`, `e2e/` — тесты
