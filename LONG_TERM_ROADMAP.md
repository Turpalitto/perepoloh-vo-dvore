## PHASE 1 — P0 STABILITY

### 1.1 Починить `npm run lint`

- **WHY** — `npm run check` (релизный гейт: typecheck + lint + test + solver +
  verify) сейчас **падает** на парсинге `scripts/run-solver-tests.mjs`. Красный
  гейт через несколько месяцев приведёт к тому, что проверку перестанут
  запускать целиком — и тогда обесценятся 534 unit-теста и 13-минутный
  solver-прогон. Это защита всей остальной защиты.
- **FILES** — `eslint.config.js`
- **RISK** — Очень низкий. Правка конфигурации линтера, игрового кода не
  касается.
- **TEST** — `npm run lint` (должен вернуть 0 без ошибок); затем
  `npm run typecheck && npm test` для подтверждения отсутствия побочных эффектов.
- **DONE** — `npm run lint` завершается с кодом 0; `.mjs`-скрипты либо покрыты
  проектным сервисом, либо явно и осознанно исключены.

### 1.2 Защитить запись в localStorage в `saveData` на платформе Яндекса

- **WHY** — `src/platform/yandex.ts:461` вызывает
  `localStorage.setItem(...)` **до** `player.setData(...)` и без `try/catch`.
  В Safari private mode, при полной квоте или под ITP `setItem` бросает
  исключение, и запись в облако **не выполняется вовсе** — авторизованный
  игрок теряет облачный сейв, хотя облако исправно. В
  `src/platform/local-fallback.ts:70` тот же вызов уже защищён — правильный
  паттерн в проекте есть, но на основной платформе не применён.
- **FILES** — `src/platform/yandex.ts`
- **RISK** — Очень низкий. Расширяет диапазон работающих сред, не сужает.
- **TEST** — новый кейс в `tests/yandex.test.ts`: замокать `localStorage.setItem`
  так, чтобы он бросал, и проверить, что (а) `saveData` не бросает наружу,
  (б) `player.setData` всё равно был вызван с корректными данными.
- **DONE** — при бросающем `setItem` облачное сохранение выполняется; ошибка
  логируется предупреждением; `saveData` не отклоняется исключением.

### 1.3 Резервная копия сейва и восстановление из повреждённых данных

- **WHY** — при битом JSON `loadData` возвращает `null`, и игра стартует с
  `defaultSave()` — то есть **полный сброс прогресса**. Вероятность низкая,
  ущерб максимальный, страховка стоит один дополнительный ключ.
- **FILES** — `src/game/save.ts`, `src/platform/yandex.ts`,
  `src/platform/local-fallback.ts`, `src/platform/mock.ts`
- **RISK** — Низкий, но требует аккуратности: `.bak` обязан обновляться
  **только провалидированными** данными, иначе он размножит повреждение.
  Red Team #4: `.bak` пишется **не на каждом `persist()`** (это удвоило бы
  запись и расход батареи), а при загрузке перед перезаписью основного ключа
  и на редких ключевых событиях.
- **TEST** — `tests/save.test.ts`: (а) битый основной ключ + валидный `.bak` ⇒
  прогресс восстановлен; (б) битые оба ⇒ чистый `defaultSave()` без исключений;
  (в) `.bak` никогда не содержит невалидные данные.
- **DONE** — повреждение основного ключа не приводит к потере прогресса при
  наличии валидного `.bak`; `SAVE_VERSION` остаётся 1 (новый ключ не меняет
  формат `SaveData` — см. Red Team #12).

### 1.4 Восстановление незавершённой попытки уровня

- **WHY** — состояние попытки живёт только в памяти `BoardView`. Проверено
  экспериментом: жёсткое закрытие вкладки внутри уровня уничтожает попытку
  целиком. На мобильном вебе Яндекс Игр eviction вкладки — рядовое событие;
  на уровне главы 10 с оптимумом 32 хода это 5–10 минут потерянной работы.
  Единственный найденный дефект, вызывающий у игрока не скуку, а обиду.
- **FILES** — `src/game/save.ts` (новый ключ `parkovka.run.v1`), `src/ui/app.ts`
- **RISK** — Средний, и Red Team выявил три ограничения, обязательные к
  реализации:
  - **#2 Дрейф данных уровня.** Если уровень изменится обновлением,
    сохранённое `GameState` станет невалидным (индексы фигур, координаты) ⇒
    неигровое состояние или краш. **Решение:** хранить отпечаток раскладки
    (число фигур + kind/len/dir/старт каждой); при несовпадении молча
    отбросить попытку и начать уровень заново. Прогресс кампании не
    затрагивается.
  - **#3 Возможность читерства.** Восстановление позволило бы «сохраняться»
    перед рискованным ходом. **Решение:** восстанавливать **только уровни
    кампании**. Испытания лиги, испытания деда (там всего 3 попытки) и
    уровень дня — не восстанавливать: там попытка есть предмет соревнования.
  - **#4 Расход записи.** **Решение:** дебаунс ~400 мс, а не запись на каждый
    ход синхронно.
- **TEST** — новый `tests/run-resume.test.ts`: (а) сохранение/восстановление
  состояния для уровня кампании; (б) несовпадение отпечатка ⇒ попытка
  отброшена, прогресс кампании цел; (в) для лиги/деда/daily состояние не
  пишется; (г) победа и выход снимают ключ. Плюс e2e: ходы → жёсткая
  перезагрузка → попытка предложена/восстановлена.
- **DONE** — попытка в кампании выживает перезагрузку; изменение данных уровня
  не приводит к краху; для соревновательных режимов восстановления нет;
  прогресс кампании ни в одном сценарии не теряется.

## PHASE 2 — CORE GAMEPLAY

### 2.1 Изменений не вносить (осознанное решение)

- **WHY** — аудит не нашёл проблем core loop, требующих правки:
  - кривая сложности: **1** скачок `+6` за 128 уровней (позиция 116, финальный
    босс — намеренный капстоун), **0** провалов `−5`;
  - средний par монотонно растёт по главам: 4.5 → 7.6 → 8.7 → 8.3 → 9.9 →
    10.4 → 11.5 → 12.1 → 16.8 → 29.1;
  - обучение реализовано через gameplay (рука-онбординг, подсказка на уровне,
    роли `tutorial`/`breather`), новая механика приходит на позициях 42/68/94;
  - победа даёт 6 слоёв фидбэка в одном оверлее (замерено в живом прогоне);
  - все 128 par доказаны BFS-решателем.

  Правка того, что работает, — чистый риск без отдачи. Порядок уровней
  менять не нужно.
- **FILES** — нет
- **RISK** — Нет
- **TEST** — регрессия: `npm test` + `npm run test:solver` остаются зелёными
- **DONE** — зафиксировано в аудите; изменения не производятся

## PHASE 3 — REPLAYABILITY FOUNDATION

### 3.1 Открыть первый дивизион Высшей лиги в середине кампании

- **WHY** — 30 мастер-испытаний, 19 ремиксов (15 из которых реально меняют
  задачу), медали, ранги и недельный чемпионат сегодня открываются только
  после финального босса на **позиции 116 из 128**. До неё доходит малая доля
  игроков ⇒ главный replay-актив проекта фактически невидим. Это
  единственная крупная упущенная возможность, и она правится доступом, а не
  производством контента.
- **FILES** — `src/game/progression.ts` (по образцу `endlessAccess`),
  `src/ui/app.ts`
- **RISK** — Средний, ограничения из Red Team обязательны:
  - **#1 Обесценивание финала.** Открывать **только первый дивизион**
    (испытания 1–5). Остальные — по существующему гейту «три медали открывают
    следующий дивизион». Финальная сцена, легендарный скин и недельный
    чемпионат остаются исключительно наградой за босса 100.
  - **#11 Не отнимать доступ у живых игроков.** Применить точный паттерн
    `endlessAccess`: `campaignDone === true` открывает безусловно, порог по
    позиции — способ открыть **раньше**, а не новое условие.
  - Порог задавать **позицией** в кампании, не `id` (вставка уровней не должна
    сдвигать момент открытия) — правило уже действует для
    `ENDLESS_TEASER_AT`/`ENDLESS_UNLOCK_AT`.
- **TEST** — unit: игрок с `campaignDone` сохраняет полный доступ; игрок на
  позиции ниже порога — доступа нет; на пороге — открыт ровно первый дивизион.
  E2E: сид сейва до порога ⇒ карточка лиги видна, дивизион 2 закрыт.
- **DONE** — первый дивизион доступен до финала; дивизионы 2+ по-прежнему за
  медалями; ни один существующий сейв не теряет доступ; финальные награды
  остаются за боссом 100.

### 3.2 Подключить «Испытания деда» к интерфейсу

- **WHY** — `src/game/grandpa-trial.ts` (103 строки) полностью реализован,
  покрыт `tests/grandpa-trial.test.ts`, а поля `grandpaTrials` уже
  санитизируются и мерджатся в `save.ts` (включая идемпотентный флаг
  `rewarded`). При этом `grep` по `src/ui/` и `src/main.ts` не находит ни одной
  ссылки: **для игрока система не существует**. Готовая, оплаченная и
  оттестированная петля мастерства лежит мёртвым грузом.
- **FILES** — `src/ui/app.ts`, `src/game/i18n.ts` (ключи `grandpaTrial.*` для
  ru/en/tr)
- **RISK** — Средний. Red Team #5: три попытки на испытание — жёсткая механика
  для казуала. **Решение:** подключать как **опциональную** ветку после лиги,
  с явным предупреждением о числе попыток, без блокировки любого другого
  контента. Награда невелика (1–3 подсказки) ⇒ цена провала тоже невелика.
  Медаль хранится как максимум, попытки не восстанавливаются (см. 1.4) —
  модель данных уже корректна.
- **TEST** — unit: расход попыток, медаль = максимум, бонус выдаётся строго
  однократно (`rewarded`), merge идемпотентен. E2E: экран доступен, попытки
  убывают, при нуле играть нельзя. Плюс `tests/i18n-parity.test.ts` должен
  остаться зелёным (все три языка).
- **DONE** — испытания доступны из UI после лиги; попытки и медали корректно
  персистятся; бонус не выдаётся дважды ни при перезагрузке, ни при облачном
  merge; тексты присутствуют на ru/en/tr.

## PHASE 5 — ДОПОЛНИТЕЛЬНЫЙ КОНТЕНТ (условный)

### 5.1 Ремикс с хрупкими досками в Высшей лиге

- **WHY** — механика `plank` реализована в core (`src/core/plank-impact.ts`,
  113 строк), покрыта тестами и скриптом `verify:planks`, но **не используется
  ни одним уровнем кампании и ни одним испытанием лиги** (проверено). Дизайн-идея
  «проехать можно один раз» сильна. `remix.ts` уже поддерживает поле `planks`,
  а `buildRemix` умеет добавлять механику и обязательную подсказку. Один спек в
  данных даёт механике жизнь — **вместо четырёх новых уровней** с той же целью.
- **FILES** — `src/levels/elite-challenges.ts`, `src/game/i18n.ts` (подсказка
  на трёх языках)
- **RISK** — Средний. Red Team #8: `par` ремикса объявляется в данных, а доски
  необратимо меняют поле ⇒ возможен тупик или **нулевая дельта оптимума** —
  ровно то, что уже случилось с ледяными уровнями до переписывания правила
  (перебор дал дельту 0 в 111 случаях из 111).
  **Жёсткое условие:** задача выполняется только если `npm run test:solver`
  подтвердит объявленный `par` **и** дельта оптимума относительно источника
  не равна нулю. Иначе — **не добавлять вовсе** и оставить механику спящей.
- **TEST** — `npm run test:solver` (шард лиги), `npm run verify:planks`,
  `tests/i18n-parity.test.ts`
- **DONE** — либо испытание добавлено и solver доказал его осмысленность, либо
  задача явно закрыта как «не подтверждено решателем». Filler-контент не
  создаётся ни при каком исходе.

### 5.2 Новые уровни кампании — НЕ создавать

- **WHY** — обоснование в разделах 14–15 аудита: 128 уровней и 1516 ходов
  оптимума дают 6–13 часов первого прохождения (выше медианы категории);
  33 комбинации механик уже представлены; маржинальная отдача 129-го уровня
  ≈ 0; производство требует дизайна + solver + ребаланса `par/par2` + трёх

  что прямо запрещено целью. Дополнительно: каждая вставка в середину
  кампании — риск для чужих сейвов (уже потребовала двух неочевидных
  исправлений: `laterLevel` по позиции и «достижения не отнимаются»).
- **FILES** — нет; `LEVEL_EXPANSION_PLAN.md` **не создаётся** осознанно
- **RISK** — Нет
- **DONE** — финальное число уровней кампании: **128**

## PHASE 7 — PERFORMANCE

### 7.1 Оптимизаций не производить (осознанное решение)

- **WHY** — замерено: `dist/` целиком **1.4 MB**, прод-бандл 480 KB
  (**115 KB gzip**), CSS 11 KB gzip, всё аудио 220 KB, крупнейший ассет
  17.9 KB, сборка 22.7 с, ноль page errors. Тяжёлых ассетов нет. Архитектура

  отдачей event loop, Endless ограничен 6×6 по соображениям скорости,

  игра поставляется архивом, а code-splitting добавил бы round-trip'ы.
  Оптимизация без замеренной проблемы прямо противоречит принципу
  «сначала докажи проблему, потом оптимизируй».

## Проверка плана на автономность

Контрольный вопрос к каждой добавляемой системе:
**«Будет ли она приносить пользу через год, если разработчик её не трогает?»**

| Система | Ответ | Почему |
|---|---|---|
| Восстановление попытки | **Да** | реагирует на действия игрока; формат состояния определяется стабильным core |
| Backup сейва | **Да** | чистая страховка, не зависит ни от чего внешнего |
| Защита `saveData` | **Да** | расширяет диапазон рабочих сред навсегда |
| Лига с середины кампании | **Да** | открывает 30 существующих испытаний бо́льшему числу игроков; данные статичны |
| Испытания деда | **Да** | данные + чистая логика; пороги деривируются из лиги |
| Ремикс с досками | **Да** | статические данные, проверенные решателем |

Ни одна из систем не требует: нового контента, серверных вызовов, ручной
балансировки, расписания выпусков, модерации.
